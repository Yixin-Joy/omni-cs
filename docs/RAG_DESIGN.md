>    `load_ready_assets()` / `save_asset_embeddings()` 是死代碼，也沒有任何地方會把
>    圖片描述向量化（`embedding_status` 永遠停在 `pending`）。現在圖片與知識塊同池排名。
> v2.10（2026-10-12）：**修掉「檢索過了卻被模型否決」** —— 答案常常「就是那張圖」，
> 純文字模型看不到圖 → 一律回 `__NO_ANSWER__` → 舊版當成未命中 → 命中得再準也不回覆

> `image`）作為保險：否決時會追問一次，仍拒絕就用題注作答；③ 送出端剝掉 markdown 圖片標記，
> 圖改走真的圖片訊息。見 §21。

## 2. 決策鏈

```
客戶來訊
  ├─ 第一層 FAQ 規則匹配 ────────── 命中 → 直接回（不呼叫模型）
  ├─ 第二層 業務表格 ────────────── 命中 → 模型依表生成
  ├─ 第三層 RAG 知識庫 ──────────── 命中 → 模型依命中文件生成   ← 新增
  └─ 第四層 降級人工
```

**層順序已定案（2026-10-08）**：`RAG` **固定排在業務表格之後**，不做成可切換 ——  
少一個會被設錯的開關，行為也更好預期。

> ⚠️ 別跟另一件事搞混：這裡講的是**決策鏈**（比對的先後）。  
> 工作台設定面板的**子頁籤排列**（知識庫要排在哪一格）是另一件事，見 §11.1。

## 3. 資料模型（新增 5 張表）

```sql
kb_collection (            -- 知識庫（分組），可整組啟停
    id BIGSERIAL PK, name TEXT, description TEXT,
    enabled BOOL DEFAULT true, sort_order INT DEFAULT 0, created_at TIMESTAMPTZ DEFAULT now()
);

kb_document (
    id BIGSERIAL PK,
    collection_id BIGINT REFERENCES kb_collection(id) ON DELETE SET NULL,
    title TEXT, filename TEXT, mime TEXT, size_bytes BIGINT, sha256 TEXT,
    source_path TEXT,                       -- media/kb/<id>/<原始檔>
    doc_type VARCHAR(10),                   -- pdf|docx|xlsx|md|txt|csv|html
    version INT DEFAULT 1, superseded_by BIGINT NULL,
    status VARCHAR(12) NOT NULL,            -- draft|parsing|chunking|embedding|ready|failed|disabled
    progress SMALLINT DEFAULT 0,
    chunk_count INT DEFAULT 0, char_count INT DEFAULT 0,
    parse_meta JSONB,                       -- 頁數／工作表／標題階層
    parse_params JSONB,                     -- ★ 這次分塊用的參數快照（之後重跑才可重現）
    error TEXT, enabled BOOL DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT now(), updated_at TIMESTAMPTZ DEFAULT now()
);

kb_chunk (
    id BIGSERIAL PK,
    doc_id BIGINT NOT NULL REFERENCES kb_document(id) ON DELETE CASCADE,
    ordinal INT NOT NULL,
    text TEXT NOT NULL,                     -- 已含 prefix（客服可編輯）
    prefix TEXT,                            -- 「產品手冊 › 第3章 藍牙耳機 › 價格」
    char_count INT,
    page_no INT, heading_path TEXT, sheet TEXT, row_from INT, row_to INT,
    embedding REAL[],
    embedding_model TEXT, embedding_dim INT,
    embedding_status VARCHAR(8) DEFAULT 'pending',   -- pending|done|failed
    edited BOOL DEFAULT false,              -- ★ 客服手改過（重跑時要問要不要覆蓋）
    enabled BOOL DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ON kb_chunk(doc_id, ordinal);

kb_job (                       -- 入庫工作佇列（重啟可續跑）
    id BIGSERIAL PK, doc_id BIGINT REFERENCES kb_document(id) ON DELETE CASCADE,
    stage VARCHAR(12), status VARCHAR(10),      -- queued|running|done|failed
    attempts INT DEFAULT 0, last_error TEXT,
    started_at TIMESTAMPTZ, finished_at TIMESTAMPTZ
);

kb_param (                      -- 參數覆寫（★ collection_id IS NULL = 全域）
    collection_id BIGINT REFERENCES kb_collection(id) ON DELETE CASCADE,   -- 可空！
    key TEXT, value TEXT, updated_at TIMESTAMPTZ DEFAULT now(),
    CONSTRAINT kb_param_scope_key UNIQUE NULLS NOT DISTINCT (collection_id, key)
);
```

**參數覆寫**：另開 `kb_param` 表。**兩層語義（v2.4 定案）**：

- `collection_id IS NULL` → **全域**：檢索參數（`top_k`／`min_score`／`max_per_doc`／
  `max_context_chars`／rerank）＋未分組文件的預設分塊參數。所有知識庫共用。
- `collection_id = 某庫` → **該知識庫的分塊參數**（塊長／重疊／策略／前綴）。

> ⚠️ 唯一鍵必須是 `UNIQUE NULLS NOT DISTINCT`（PG 15+）。用一般 `PRIMARY KEY(collection_id, key)`
> 存不了 NULL，而且 PG 的 NULL 互不相等 → 同一組全域參數能插無限多筆。
> 舊庫升級走 `kb_db._MIGRATE`（先拆舊 PK，再 `DROP NOT NULL`，順序不能顛倒）。
> 分派規則的唯一實作在 `kb_db._param_target()`。

**不新增查詢日誌表**：RAG 的命中寫進 `autoreply_log`（`tier='rag'`、`score=top1`、`matched_rows=候選清單`）。

## 4. 需求 1 前半：參數可調（含 UI）

### 4.0 放哪裡（已定案 2026-10-08）

**與文檔解析無關的參數，不放在上傳向導裡。** 向導只管「這份文件怎麼切」；  
檢索類參數一律移到**知識庫概覽頁的「參數配置」按鈕**，隨時可調。

| 參數組                                  | 放在哪                                         | 範圍                       | 改了之後的後果                  |
| ------------------------------------ | ------------------------------------------- | ------------------------ | ------------------------ |
| **檢索參數**（top-k／門檻／單檔上限／上下文上限／rerank） | **知識庫概覽頁 →「參數配置」彈窗 A 區**                        | **全域（所有知識庫共用一組）**            | **5 秒生效，不用重啟、不用重建**      |
| **分塊參數**（塊長／重疊／分塊策略／前綴）              | **分塊配置界面**（單一文件的分塊那一步就地調；「存為本庫預設」寫回 `kb_param`） | **按知識庫**（未分組 → 全域那批）         | 要**重新切塊 ＋ 重跑 embedding** |

> 好處：上傳時客服只需要判斷「切得好不好」，不用面對 top-k 這種他不該懂的旋鈕。  
> 檢索參數**不分知識庫** —— 問句會撈全部啟用庫的塊，本來就不存在「這個門檻只適用 A 庫」的語義；
> 「A 庫嚴格、B 庫寬鬆」在舊版只是**假象**（最終由 doc_id 最小的庫決定）。

### 4.1 為什麼不能只改 `.env`

`config.py` 的 `_get()` 在 **import 時就求值**，所以 `.env` 的值在服務啟動那一刻就固定了。要做到  
「UI 改了立刻生效、不用重啟」，必須是：

```
執行時取值 = DB 有設定 ? DB 值 : .env 預設值
             ↑ 走 reply_engine._cache（5 秒 TTL）
```

- `.env` → 提供**預設值**（與你放提示詞的習慣一致，也讓新環境開箱可用）
- DB → 提供**覆寫值**，UI 寫這裡
- 快取 5 秒 → 改完下一則訊息就生效，**不必重啟服務**

| ---- | ------------------------------------------------------------- |
| ① 清單 | **知識庫概覽卡**（模型、統計、索引規模）＋ 知識庫卡清單；有未分組文件時多一張「未分組」卡               |

### 5.3 「未分組」是一個虛擬知識庫

上傳時可以**不選知識庫**，那些文件 `collection_id` 是 `NULL`，不會被第三層檢索碰到。  
① 清單頁右下會多一張「未分組」卡（`totals.ungrouped_docs > 0` 時才出現），點進去是 ② 文件頁

> → `WHERE d.collection_id IS NULL`；`overview.totals` 另給 `ungrouped_docs` 計數。

### 5.4 原本的四步向導（同一頁版本，已被 §5.0 取代，保留作為流程說明）

**四步**（參數配置已從向導移除，見 §5.2），**全部在 draft 態**，最後一步才上線：

```
① 上傳 ──▶ ② 分塊預覽與微調 ──▶ ③ 開始 embedding ──▶ ④ 確認入庫
              ↑ 分塊參數在這裡就地調（改了立刻重切、立刻看效果）
```

| 步           | 內容                                                          | 細節                                 |
| ----------- | ----------------------------------------------------------- | ---------------------------------- |
| ① 上傳        | 拖曳多檔（pdf/docx/xlsx/md/txt/csv/html），選／新建**目標知識庫**，立即存檔 + 解析 | 每檔顯示頁數／字數／工作表；解析失敗給人話原因            |
| ② 分塊預覽與微調   | 逐塊預覽，可**編輯／拆分／合併／刪除／停用**，顯示字數與來源                            | 塊長／重疊／策略就在這頁調（見 §4.2 B）；標 `edited` |
| ③ Embedding | 顯示模型、塊數、進度；可中斷、可只重跑失敗塊                                      | 寫 `embedding_status`               |
| ④ 確認入庫      | 摘要（N 檔／M 塊／用哪個模型）→ 上線                                       | 只把 `status` 改成 `ready`             |


**技術要點：draft 直接寫 `kb_chunk`。** 微調即時落庫（不是存在瀏覽器記憶體），
所以「改到一半關掉、明天再回來」不會丟。第 ④ 步只是一個 status 切換，失敗不會有半成品上線。

**「目標知識庫」為什麼留在向導裡**：它是**歸屬**不是**參數** —— 決定這批文件進哪個庫、
之後吃哪一組參數。所以第 ① 步就選，後面的分塊參數預設值也從該庫的 `kb_param` 帶出。

## 6. 分塊策略（依類型）

| 類型 | 解析器 | 切法 | 保留 metadata |
|---|---|---|---|
| PDF | `pypdf` | 逐頁抽文字 → 按段落合併至目標長度 | `page_no` |
| DOCX | `python-docx` | 按 Heading 1/2/3 階層切；表格轉 markdown | `heading_path` |
| XLSX | `openpyxl` | 每 sheet 一組；標題列當欄名，每列組成「欄名：值」句，每 10–20 列一塊 | `sheet / row_from / row_to` |
| MD | 內建 | 按 `##` 切；程式碼區塊整塊不切 | `heading_path` |
| TXT | 內建 | 按空行段落合併 | — |
| CSV | 內建 | 同 XLSX | 列座標 |

**每塊前置前綴**：`{文件標題} › {章節路徑}`，**與內文一起 embed**（對短問句召回提升明顯）。

**掃描型 PDF**（無文字層）→ 解析 0 字元時**不靜默通過**，標 `failed` + `error='no_text_layer'`，
UI 顯示「讀不到文字，可能是掃描件」。OCR 列為後續選配。

### 6.1 合併與重疊的鐵則（2026-10-08 實測踩過）

把相鄰區塊併到目標長度時，**重疊（overlap）只能這樣做**：

```
開新塊的那一刻：buf = 上一塊的尾端(overlap 字) + "\n" + 這一塊
累積途中：      buf += "\n" + 這一塊      ← 只累加，永不刪減
```

❌ **不可以**在累積途中拿尾端去「取代」緩衝區（`buf = tail(buf, overlap) + text`）——
那會把還沒收成塊的內容整段丟掉。這是「重疊」寫成「截斷」的經典錯誤：

| | 原始 | 分塊後內文 | 說明 |
|---|---|---|---|
| 舊寫法 | 600 字 | **281 字** | A、B 兩段整段消失 |
| 舊寫法（真實文件） | 4796 字 | **2125 字** | 161 段裡 86 段沒進任何塊 |
| 修好後 | 4796 字 | 5082 字 | 多出來的是重疊（正常） |

⚠️ 還有第二個坑：尾端的零頭塊（< `chunk_min`）會被併回**前一塊**。若它開頭帶著
上一塊的重疊，併回去就會變成「一塊自己重複自己尾巴」。所以必須記住
「這一塊開頭實際放進多少重疊」（`carry_used`），**合併時把它拿掉**。

✅ 回歸閘門：`kb_check.py` 的 **[1b]** 段 —— 三種策略 × 重疊 0/60 檢查
「不得丟內容」「不得自我重複」「塊長 ≤ chunk_max」。改動 `kb_chunk.py` 必跑這支。

⚠️ **既有文件要用新版重切**（分塊內容變了，向量的語義也跟著變）：
UI 是「重新分塊（寫庫）」→「開始向量化」→「確認入庫」。重切會把手改過的塊覆蓋掉
（API 有 `edited > 0` 的擋門，要 `force` 才過）。

## 7. 檢索（含 rerank 介面預留）

```
q →[勾了查詢改寫]→ 改寫出 N 條 → 多條各自混合召回 → 同塊取最高分 → 去重/截斷
                                                          → [rerank] → 門檻判斷 → 生成
q →[沒勾]→ 混合召回 → 去重/截斷 → [rerank] → 門檻判斷 → 生成
                                    └ 首次未過門檻且有對話 → 改寫一句再查一次（舊行為）
```

1. **改寫（可選，勾了才做）**：見 §7.8。沒勾時保留舊行為 —— 第一次沒過門檻才用
   `rewrite_table_query(question, history_text)` 補救一次。
2. **混合召回**：`final = 0.65 × cosine + 0.35 × lexical`，`lexical` 用 `faq_matcher.preprocess/score_pair`（jieba + 繁簡正規化）。多條查詢時**每條各算一次**，同一個塊取最高分（`kb_search.search_multi()`）。
3. **去重**：同文件最多 3 塊；`top_k=6`；總字數 ≤ `RAG_MAX_CONTEXT_CHARS`。
4. **門檻**：`top1 >= RAG_MIN_SCORE`；未過 → **不呼叫模型**，直接降級人工。

5. ⚠️ **門檻預設值已用實測校正（0.55 → 0.28）**。設計稿原本估的 0.55 是在「以為 cosine 就是
   最終分數」的前提下寫的，但實際公式是 `0.65 × cosine + 0.35 × 字面`，**上限會被壓縮**：
   連近乎完美的命中（vec 0.735 / lex 0.372）也只到 **0.608**。用 0.55 的話，8 條相關問句只有
   2 條過關 —— 第三層等於沒開。`kb_search_check.py` 實測：

   | | top-1 分數 |
   |---|---|
   | 相關問句（8 條） | 0.168 / 0.340 / 0.342 / 0.353 / 0.417 / 0.495 / 0.607 / 0.608 |
   | 不相關問句（3 條） | 0.107 / 0.131 / 0.193 |

   取「相關最低」與「不相關最高」的中點（≈0.27）→ **0.28**：相關過 7/8、不相關擋 3/3。
   落在那條線外的例子是「**不想要了可以退嗎**」（0.168，vec 0.255）——
   口語改寫、且與原文「7 天內可無理由退貨」幾乎沒有共同字面，所以向量分也偏低。
   這種問句要靠 FAQ 層（人工維護問法）覆蓋，不是把門檻壓低就能解決（壓低會連不相關的都放進來）。
   **P4 校準請用自己的真實問句重跑 `kb_search_check.py`**，別沿用這組數字。
5. **rerank 介面（先留好、預設不啟用）**：
   ```python
   class Reranker(Protocol):
       def rerank(self, query: str, chunks: list, top_n: int) -> list: ...
   class NoopReranker:      # 預設實作
       def rerank(self, query, chunks, top_n): return chunks[:top_n]
   # 之後要裝：FastEmbedCrossEncoder("BAAI/bge-reranker-v2-m3-int8")
   ```
6. **掛掉時自動降級**：embedding 服務不可用 → 退回純字面檢索（`pg_trgm` + jieba），RAG 層不會整層失效。

### ⚠️ 成本預告（你同意第一版不裝的理由）
CPU 上 cross-encoder 要對每個 (query, chunk) 跑一次完整前向。以 top-20 × 500 字估：
**單次檢索 +1~3 秒**。多個客戶同時問會排隊。若哪天要裝，建議只 rerank top-20 且設總逾時（超時就跳過）。

### 7.8 查詢改寫（多查詢檢索，可選開關）

**開關**：`query_rewrite`（檢索參數・全域，預設**關**）。UI 在「參數配置 → A. 檢索參數」，
命中測試頁另有「這次強制開啟／關閉」可單獨比較（不動正式設定）。

**為什麼要放在檢索「前」而不是查不到才補救**：錯別字型的問句（「藍芽耳機多少千」）
第一次就註定撈不到；等沒過門檻才改寫，等於讓每次檢索都先付一次無用的召回 + 5 秒 TTL 快取
還要多跑一輪。放在前面則一次檢索就把該補的一次補完。

**流程**：`rewrite_rag_queries()` 依上下文吐出 N（`RAG_QUERY_REWRITE_N`，預設 2）條查詢 →
`[原問句] + [改寫句…]` 一起去 `kb_search.search_multi()` → **同一個塊取最高分** →
合併後才做一次 top_k / max_per_doc / rerank / 上下文截斷。

⚠️ **順序不能顛倒**：若每條 query 各自 `_pick(top_k)` 再合併，召回數會悄悄變成 N 倍、
`max_per_doc` 也形同失效。這是 `kb_search._finish()` 唯一的收尾入口的用意。

**提示詞重點（`rag_config.RAG_REWRITE_PROMPT`）**，照優先序：

1. **同音／近音錯別字** —— 客戶用手機打字，錯的往往是關鍵名詞（藍芽→藍牙、腿貨→退貨、
   飽固→保固、多少千→多少錢）。提示詞裡直接列一組常見錯法當示範，並要求
   **拿不準就兩種寫法各出一條**（一條留原字、一條用正確詞）—— 這樣「改對」與「改錯」都不會
   把檢索堵死，是這條規則能以「多查詢」形式落地的前提。
2. **上下文補齊** —— 「這個多少錢」「那可以退嗎」的主語在對話裡；要求從最近對話補進查詢句，
   補不出來就維持原樣、**不准编造**品名價格（與表格層的改寫同一套約束）。
3. 只輸出 N 行、不要編號引號說明、不要客套、N 行不可相同。

**輸出解析**（`deepseek_client.clean_rewrite_list`）：模型常多寫編號（`1.`／`1、`／`-`／`①`）、
引號、JSON 陣列、或一句「以下是改寫結果：」。全部容忍 —— 逐行剝掉標記與引號、丟掉以
說明詞開頭或超過 60 字的行、去重、排除與原問句相同的行，最後截到 N 條。
⚠️ 判斷「說明行」**只比對行首**（`保固說明` 是正常問句、`查詢訂單` 也是）。

**溯源**：`Hit.queries` 記下「這塊被哪幾條查詢撈到」，寫進 `matched_rows`。
UI 在出現多查詢時，每個候選塊多一行「命中查詢：…」——一眼看得出某塊是靠改寫句救回來的，
還是原問句本來就撈得到。`SearchResult.queries` 則是這次實際用的全部查詢句（第 0 條固定是原句）。

**調參入口**：`POST /console/kb/search` 帶 `rewrite=1`（可再帶 `history` 純文字或
`[{direction,text}]`）會直接回改寫結果與合併後的召回明細，用來肉眼確認提示詞有沒有抓到錯字。

### 7.9 一次改寫、三層共用（2026-10-08 定案）

**問題**：舊做法是「每層各自改寫」—— FAQ 一次、表格一次、知識庫一次，
實測一次回覆因此吃掉 8 次模型呼叫 / 48.9 秒。

**做法**：整個流程只改寫**一次**，那一組查詢三層共用。

```
客戶來訊
  │
  ├─ 第一層 FAQ：用**原句**做規則匹配 ──命中──▶ 回覆（0 次模型呼叫）
  │                                    │
  │                                  未命中
  │                                    ▼
  ├─ ★ 改寫一次（唯一的一次）→ queries = [原句] + [改寫句 × N]
  │     │
  │     ├─ FAQ 拿 queries 再匹配一次（純規則，不再呼叫模型）
  │     ├─ 第二層 表格：queries 逐條生成，**第一條命中就停**（上限 `RAG_TABLE_QUERY_MAX`）
  │     └─ 第三層 知識庫：search_multi(queries) 一起檢索 → 生成（用**原問句**生成）
  │
  └─ 都沒有 ──▶ 降級人工
```

**幾個關鍵決定**：

| 決定 | 理由 |
|---|---|
| FAQ **先**用原句匹配，未命中才改寫 | FAQ 是規則匹配、命中率不低；命中時完全不必花改寫的錢（原本固定花 4.8 秒）|
| 生成用**原問句**（不是改寫句）| 改寫只是為了「查得到」；回答要針對客戶真正問的那句話，免得答成另一種說法的問題 |
| 表格層逐條「生成」要設上限 | 生成比檢索貴得多（每條一次呼叫）；表格真的沒這筆資料時，試完幾條也問不出來 |
| 知識庫檢索可以全用 | 檢索便宜（本地向量+字面），多一條查詢幾乎不增加成本 |
| 改寫開關**統一成一個** | 原本 FAQ 另有 `FAQ_REWRITE_MODE`（.env），兩個開關會讓人搞不清「我明明關了為什麼還在呼叫模型」|
| 改寫提示詞**只有一條**（`rewrite_prompt`，可頁面編輯）| 原本 FAQ 專用／表格專用各一條（`DEEPSEEK_REWRITE_PROMPT`／`DEEPSEEK_TABLE_REWRITE_PROMPT`，已刪）。現在只剩 `rag_config.RAG_REWRITE_PROMPT` 一條，三層共用；它同時也是**參數**，可在「參數配置 → C. 提示詞」改、約 5 秒生效 |
| 知識庫層**不再有**「首次未過門檻 → 單句改寫重查」的兜底 | 它讓「關了改寫卻還在呼叫模型」無法解釋，而且用的是另一條提示詞。要改寫就開 `query_rewrite`，一次改寫三層共用 |

**實測（mock 確定性驗證 + 真實模型）**：

| 情境 | 模型呼叫 | 說明 |
|---|---|---|
| FAQ 命中 | **0 次**（0.07 秒）| 純規則匹配，完全不碰模型 |
| FAQ 未命中（表格+知識庫都跑）| **≤4 次**（優化前 8 次）| 改寫1 + 表格≤2 + 知識庫1 |

⚠️ **這台閘道的改寫呼叫常超過 5 秒**（實測 ReadTimeout）—— `DEEPSEEK_AUX_TIMEOUT`
預設 5 秒在健康閘道上夠用，但若你的閘道較慢，改寫會頻繁失敗（失敗＝沿用原問句，
不會壞掉，只是白花 5 秒）。要調就改 `.env` 的 `DEEPSEEK_AUX_TIMEOUT`。

⚠️ **自檢要能分辨「環境失敗」與「邏輯失敗」**：閘道限流（429）／逾時會讓涉及模型的
斷言失敗，但那是環境問題、不是程式壞了。`engine_check.py` 的 `check_or_env()`
遇到 429/ReadTimeout 會標 **[環境]** 並在總結單獨列出（**不算 FAIL**）。

知識庫問答的 system prompt（`rag_answer_prompt`）**是可編輯的參數**（2026-10-08 起）：

| | |
| ---------------------------------------------------------- | ------------------------------------------------------------------- |
| 存哪 | `kb_param`，`collection_id IS NULL`（**全域**，所有知識庫共用一組） |
| 內建預設 | `rag_config.RAG_PROMPT`（`.env` 可用 `DEEPSEEK_RAG_PROMPT` 覆寫） |
| 取用 | `kb_search.prompt_of("rag_answer_prompt")` ← `deepseek_client._db_prompt()` 是唯一入口 |
| 編輯 | 工作台「知識庫 → 參數配置 → **C. 提示詞**」多行輸入框；約 5 秒生效、不用重啟、不用重建 |
| 保護 | 少了 `{context}` / `{sentinel}` → 寫入端回 **400**；讀取端 `prompt_value()` 再退回預設（DB 被手改也擋得住） |

內建預設的骨架（可在頁面改，但**必須保留** `{context}` 與 `{sentinel}`）：

```
以下是知识库检索到的资料（每段前有编号与来源）：
─────
{context}
─────
请「只根据上述资料」回答使用者的问题。

═══ 忠实原则（最重要）═══
1. 事实必须能在资料里找到出处；资料没写的一律不说
2. 与自有知识冲突时，一律以资料为准
3. 资料只讲了一半，就只讲那一半 —— 不补全、不推测

═══ 原样输出（涉及设计 / 数据结构 / 技术细节时必守）═══
数据结构 / 字段定义 / 接口协议 / 请求响应示例 / 参数配置 / 代码 / 报错 /
版本号 / 文件路径 / 精确数值 →
· 先把资料里的对应内容原封不动抄出来，再另起一段用文字解释
· 原样保留：字段名与嵌套结构、大小写、下划线、引号、缩进、换行、单位、示例值
· 禁止：改写字段名、用「…」省略字段、把 JSON 改成句子、把代码改成伪代码
· 资料里的代码块 / JSON / 表格，照样用代码块或表格输出

═══ 语气与格式 ═══ …（通顺礼貌、问什么答什么、不带 '*' '-'）
═══ 最高优先规则 ═══ 资料答不了 → 只输出 {sentinel}（沿用 __NO_ANSWER__）
```

- **為什麼「原樣輸出」要寫得這麼硬**：知識庫裡放的是對接手冊、接口文檔這類**逐字都要對**
  的內容。模型很愛「順手美化」—— 把 `conversationId` 寫成「對話編號」、把一段 JSON 壓成
  一句話、把接口路徑換個說法。對客服來說那是災難（客人照著填就錯）。所以規則定成
  **「先原文、後說明」**，並把禁止事項逐條列出來。
- 取值一律用 `replace` 不用 `str.format`：使用者自訂的提示詞裡只要有一個孤立的 `{`，
  `format()` 就會直接炸掉整層（`deepseek_client._fill()`）。
- `{sentinel}` 沿用 `__NO_ANSWER__`，`reply_engine._tidy()` 直接可用。
- 貼文留言場景沿用 `DEEPSEEK_COMMENT_PROMPT`（公開場合不報價等）。
- **對客戶不顯示來源**；來源寫進記錄，客服側可查。

## 12. 模型選型（實測數據）

### 12.1 先講結論：我改建議 `jina-embeddings-v2-base-zh`

你問「`bge-small-zh-v1.5` 效果如何、跟 jina 差別大不大」——
**差別不小，而且因為你決定第一版不裝 reranker，這個差距會被放大**（沒有第二道防線修正召回）。

| | `BAAI/bge-small-zh-v1.5` | `jinaai/jina-embeddings-v2-base-zh` |
|---|---|---|
| 參數量 | 24M | 161M |
| 向量維度 | 512 | 768 |
| **最大輸入長度** | **512 token** ⚠️ | **8192 token** |
| 語言 | 中文（英文偏弱） | 中英雙語 |
| 下載大小（fastembed 實測） | **95MB** | **640MB** |
| C-MTEB 中文檢索 | 自家 6 任務表 Retrieval **61.77**／Avg 57.82 | 官方自報 C-MTEB **63.79**（≈ bge-large-zh 檔次） |
| 常駐記憶體 | 約 +0.2GB | 約 +0.9GB |
| 入庫速度（12 核 CPU 估） | 約 0.03 秒/塊 | 約 0.15 秒/塊 |

> 兩邊分數來自不同聚合方式（BGE 自家 6 任務表 vs MTEB 排行榜），**不能逐位相比**，
> 但檔次差距明確：jina-zh 與 bge-**large**-zh 同級，bge-**small**-zh 低一檔。

**三個決定性理由**：

1. **512 token 是硬傷**。你要的塊長「可調、預設 500 字」——中文在 BERT 系 tokenizer 下約 1 字 ≈ 1 token，
   用 bge-small 的話**塊長一超過 500 就被無聲截斷**，等於後面調的參數有一半是假的。jina 的 8192 沒這問題。
2. **沒有 reranker 兜底**。第一版不裝 rerank，召回品質 100% 由 embedding 決定，這時候不能省。
3. **成本可接受**。640MB／12 核／16GB RAM 完全吃得下；而且**檢索延遲差別很小**
   （每次只編碼一句短問句），差的是「入庫時間」與「常駐記憶體 ~0.9GB」，兩者都可接受。

### 12.2 已核實的完整選單（fastembed 0.9.0）

**重要發現：fastembed 的 zh 系列只有 `bge-small-zh-v1.5` 一個**，`bge-base-zh` / `bge-large-zh` 都不支援
（要自己轉 ONNX）。所以中文選項實際上就這幾個：

| 模型 | dim | 下載大小 | 語言 | 上限 |
|---|---|---|---|---|
| `BAAI/bge-small-zh-v1.5` | 512 | 95MB | 中文 | 512 token |
| `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` | 384 | 220MB | 50+ 語言 | 128 token（太小） |
| **`jinaai/jina-embeddings-v2-base-zh`** | 768 | **640MB** | 中英 | 8192 token |
| `intfloat/multilingual-e5-large` | 1024 | 2.24GB | 100+ 語言 | 512 token |
| `jinaai/jina-embeddings-v3` | 1024 | 2.29GB | 多語 | 8192 token |

## 18. 回應延遲：實測與優化（2026-10-08）

### 18.1 實測：一次知識庫回覆 = 8 次模型呼叫 / 48.9 秒

| # | 呼叫 | 耗時 | 誰發的 |
|---|---|---|---|
| 1 | FAQ 改寫 | 4.80s | 第一層：規則未命中就想改寫後再匹配一次 |
| 2 | 表格 生成答案 | 2.28s | 第二層：把表格丟給模型問一次 |
| 3 | 表格 單句改寫 | 7.41s | 第二層：未命中 → 改寫問句 |
| 4 | 表格 生成答案 | 2.26s | 第二層：**拿改寫後的問句再問一次** |
| 5 | RAG 多查詢改寫 | 30.03s | 第三層：**ReadTimeout → 又重試一次** |
| 6-8 | RAG 生成答案等 | — | 撞上閘道 429 限流 |
| | **非模型部分（檢索／jieba／DB）** | **2.05s** | |

兩個放大器：
- `DEEPSEEK_TIMEOUT=30` ＋ 呼叫失敗**自動重試一次** → 單一呼叫最壞吃 **61 秒**
- 閘道 `max_parallel_requests=2` → 第二個客人進來就 429

**檢索本身不是瓶頸**（2.05 秒，含首次模型載入）；瓶頸是「每一層失敗都要再問一次模型」。

### 18.2 已做的優化

| 改動 | 效果 |
|---|---|
| **輔助呼叫（改寫）短超時 5 秒 + 不重試**（`DEEPSEEK_AUX_TIMEOUT`） | 實測：改寫 ReadTimeout **5.2 秒就放棄**、沿用原問句（原本 30+30=60 秒） |
| **表格層「改寫後重問」只在有對話歷史時才做** | 沒有對話就沒有指代可補，模型只能換句話說 → 幾乎必然再次未命中，純浪費 9.7 秒 |
| **本地併發閘門**（`DEEPSEEK_MAX_CONCURRENCY`，預設 2） | 在本地排隊，不去撞閘道的限流線 |
| **429 退避**（解析閘道給的 `Limit resets at`） | 撞到限流時等待正確的時間再試，而非盲目重試 |
| **啟動背景預熱**（embedding 模型 + 檢索索引） | 第一次查詢不再付 2.3 秒的模型載入（實測預熱 0.54 秒） |
| **`autoreply_log` 記 `elapsed_ms / llm_calls / llm_seconds`** | 紀錄頁直接顯示「耗時 48.9s，模型呼叫 8 次」——以後不用再猜 |

⚠️ **輔助呼叫與必要呼叫必須分開對待**：改寫是「錦上添花」，失敗沿用原問句就好；
給它 30 秒超時 + 自動重試，等於讓一件不重要的事把整則回覆拖垮。

### 18.3 還能再做的（未實作，等你決定）

| 方案 | 省下 | 代價 |
|---|---|---|

## 19. 圖文結合輸出（2026-10-12）

### 19.1 為什麼不做 OCR（先講結論）

「圖文結合輸出」與「OCR」是**兩件不同的事**，一開始很容易混在一起：

| | 解什麼問題 | 需不需要 AI |
|---|---|---|
| **圖能被檢索、能被帶出來** | 抽圖 → 綁到知識塊 → 命中時一起輸出 | **不需要** |
| **圖裡的內容能被搜到** | 對圖做描述（或 OCR）→ 描述進檢索 | 需要（視覺模型） |
| **掃描件（整頁是圖、沒有文字層）** | 把圖變成文字 | 需要 OCR |

**實測後定案：現階段不需要引入 OCR。** 理由：

1. **手上沒有需要 OCR 的檔案**：目前知識庫 0 筆 `no_text_layer` 失敗；
   唯一真實的中文 PDF（教育部通知）**有文字層**（6 頁 / 2448 字）。
2. **模型本身就能讀圖中文字**：把 PDF 抽出的圖（16KB jpg）以 base64 餵進 `image_url`，
   正確讀出圖中文字「教育部文件」並描述畫面。所以「圖裡的文字要能被檢索到」這件事，
   用**圖片描述**（提示詞要求它把圖中文字照抄）就解決了，不必另裝 PaddleOCR。
3. OCR 只在「**大量**掃描件」或「需要**精確逐字**（發票號、證件號）」時才值得；
   真要做再選 PaddleOCR（中文強、本地免費）。

⇒ 三個模組是**可各自獨立取用**的：① 抽圖＋呈現（成本 0）② 圖片描述（進檢索）
③ OCR（暫不做）。

### 19.2 資料模型

```
kb_asset                                  -- 圖（兩條來源共用一張表）
  collection_id / doc_id                  -- doc_id 有值 = 從文件抽的；NULL = 單獨上傳
  page_no / bbox                          -- PDF 座標（溯源用）
  rel_path / filename / mime / size_bytes / width / height / sha256
  caption                                 -- 描述（題注 / 人工 / AI）
  caption_source                          -- doc | manual | ai
  caption_status                          -- pending | done | failed
  embedding / embedding_status            -- 描述也能被檢索
  enabled / filtered_reason               -- 被啟發式判為裝飾圖時 enabled=false
kb_asset_chunk (asset_id, chunk_id)       -- 圖 ↔ 知識塊（多對多）
```

**`caption_source` 是刻意的**：跟 `kb_chunk.edited` 同一個保護思路 ——
`manual` 的不會被「AI 描述」覆蓋（要覆蓋得明示 `force=1`）。

### 19.3 圖一定要綁到分塊（使用者 指定的硬規則）

「從文檔提取的圖**一定**要和分塊綁定，確保命中後圖片結合輸出」。

綁定的依據是**解析階段記下的錨點** `ParsedAsset.anchor_block`（這張圖最靠近哪個 Block）：

- **PDF**：有座標 → 取同頁上「離圖最近」的那一塊（比塊的上緣與下緣，誰近算誰）。
- **DOCX**：沒有頁碼 → 取「目前最後一個 Block」（圖通常緊接在它的說明文字之後）。
- 落地時 `Chunk.block_from / block_to`（該塊涵蓋輸入 blocks 的哪個區間）把兩邊接起來。
- 錨點失效時退化成「同頁碼的塊」；再不行就 `POST /asset/rebind` 重算。

### 19.4 題注優先（使用者提的）

文件裡本來就有圖說（「圖 3-2 請求流程」）時，**直接用題注當描述**，不必花 AI：

- **PDF**：找圖片下緣 70pt 內、符合題注樣式的行（也接受在上方）。
- **DOCX**：先看圖片**同一段**的文字，再看**後面幾段**。
- 樣式：`图|圖|表|figure|fig.|table|exhibit|chart|image|图片|圖片` + 編號 + 說明。

### 19.5 裝飾圖過濾（啟發式，寧可留下不要誤刪）

| 規則 | 門檻 |
|---|---|
| 太小 | 任一邊 < 60×40 px |
| 長寬比極端 | ≥ 8:1（分隔線那類） |
| 面積過小 | 顯示面積佔頁面 < 1.2% |
| 頁首扁橫幅 | 在最上方 25%、高度 < 頁高 12%、寬度 > 頁寬 50%、且沒有題注（紅頭文件抬頭） |
| 重複出現 | 同一 sha256 出現 ≥ 3 次（PDF）／≥ 5 次（DOCX）→ LOGO／浮水印 |

**判為裝飾只是 `enabled=false`，記錄與檔案都留著** —— UI 有「顯示被過濾的」可以複查、
一鍵啟用（誤判的代價只是多一張圖，誤刪是資料損失）。

### 19.6 描述：預設人工，AI 是按鈕

上傳／入庫時**完全不會呼叫模型**（大量圖的文件才不會爆成本）。
描述的三條來路：題注（自動）→ 人工（預設）→ AI（按鈕，`describe_image()`）。

AI 描述的提示詞（`image_caption_prompt`）要求**把圖中文字照抄進描述**，
等於順手讓「圖裡的字」也變成可檢索內容。
⚠️ 本專案用的是 **reasoning 模型**，`max_tokens` 太小會被思考過程吃光、回空字串
（實測 20/30 就會空 → 預設給 1500）。

### 19.7 輸出端

- **工作台**：`SearchResult.assets` / `Hit.assets` → 召回明細顯示縮圖；文件分塊頁有一條圖片縮圖。
- **自動回復**：`Answer.assets` → `autoreply._send_assets()`（**只有私訊**才發圖，
  留言是公開場合不發）。WhatsApp 走 `upload_media`+`send_image`、微信走 `send_image`；
  **IG/FB 略過**（它們的 attachment 要公開可抓的 URL，本服務沒有公開圖床）。
- ⚠️ 圖送失敗**不算回覆失敗** —— 文字已送到，圖只是加分項。

### 19.8 已知取捨

| 項目 | 現況 | 之後可以 |
|---|---|---|
| 圖的讀取 | 走 `/console/kb/asset/file/{id}`（不經公開的 `/files`） | 真的要鑑權再加 |
| 圖片檢索 | 只靠 caption 進向量（尚未把圖本身做成 CLIP 向量） | 要就接 `jina-clip-v1`（fastembed 有，768 維） |
| OCR | 不做（模型能讀圖中文字） | 大量掃描件時接 PaddleOCR |
| 表格轉圖 | XLSX 的圖表不抽（資料本身已有結構化管道） | 需要再說 |

### 19.9 PDF 行級解析（§6.2 的實作）

舊版 `page.extract_text()` 有兩個問題：把頁碼／頁眉頁腳混進內文、
**每一頁自己成一段**（跨頁的句子被硬切成兩段）。

改成 `pdfplumber` 的行級物件（text + `top/bottom/x0/x1`）之後：

1. **頁碼**：落在頁邊帶（上 9% / 下 14%）**且**符合頁碼樣式（`— 2 —`／`第 2 頁`／`Page 2`／羅馬數字）。
2. **頁眉頁腳**：邊界帶內、同一段文字出現 ≥ 3 頁。
3. **跨頁續接**（★ 方案 A 的核心）：上一頁最後一行 + 本頁第一行，四個條件都成立才接起來 ——
   ① 上一行沒有以句末標點收尾 ② 本行不是段落起始特徵（`第X條`／`一、`／`1.`）
   ③ 上一行確實在頁底（≥ 82%）④ 本行確實在頁首（≤ 22%）。
   **接起來時不產生 `\n\n`**（中文不插空格、英文插一個空格）；只有真正的語義段落結束才雙換行。
4. **段落邊界**：行距明顯變大（> 1.5× 中位行距）、首行縮排（> 18pt）、
   以段落起始特徵開頭、或上一行已以句末標點收尾。

⚠️ ASCII 句點要另判：`.` 只在**前一個字是英文字母**時才算句末
（否則 `0.5`／`v1.2`／`192.168.1.1` 會被誤判成句子結束）。

驗證（`tests/kb_asset_check.py` [1]）：合成的雙頁 PDF，p1 尾句在頁底、p2 首行在頁首 →
`cross_page_joins=1`、兩行接成同一段；頁碼 `- 2 -` 被丟掉；
**逐頁去空白比對舊算法，差額恰好等於頁碼字數（零遺漏）**。
真實案例：教育部 PDF 6 頁 / 2448 字 → 頁碼 5 個全濾除、跨頁那句完整接起。

## 20. 圖片：內嵌 markdown ＋ 知識庫分兩型（2026-10-12）

### 20.1 為什麼要改（v2.8 的做法不夠）

v2.8 把圖片當「獨立資產」，靠 `kb_asset_chunk` 綁到知識塊，命中時另外把圖清單塞進
`SearchResult.assets`。問題：

1. **圖片庫根本搜不到。** `kb_search` 從來沒查過 `kb_asset`：
   `load_ready_assets()` / `save_asset_embeddings()` 是**死代碼**，而且沒有任何地方
   會把圖片的描述向量化 → `embedding_status` 永遠停在 `pending`。
   實測：上傳一張截圖、寫了描述「圖文合并輸出效果截圖」，問「图文结合输出效果如何」
   **查不到**（top1 是別的東西）。
2. **圖與文是兩條通道**（文字走 `hits`、圖走 `assets`），前端要特別處理，
   而且 LLM 看到的 context 裡沒有「這裡有一張圖」的線索。

### 20.2 新做法：把圖寫進 chunk 文字

```
解析 → ParsedAsset（帶 anchor_block）
     ↓
分塊時：![題注](/media/<sha16>.png) 接到「它最靠近的那個 Block」尾端
     ↓
chunk.text  ← 完整 markdown（存 DB、給 LLM、給前端）
     ↓
embedding  ← strip_md_images(chunk.text)  只吃文字
```

- **命名**：`![題注](url)`；**沒有題注就 `![](url)`** —— 不亂標名字。
- **位置**：靠解析階段記下的 `anchor_block` + `Chunk.block_from/block_to`；
  分塊後那張圖自然落在「涵蓋該 Block 的那一塊」。
  被啟發式判為裝飾的圖（LOGO／分隔線／抬頭）**不注入**。
- **只對文字向量化**：`kb_chunk.strip_md_images()` 在 embedding 與字面比對前剝掉標記。
  理由：`xxx.png` 與 URL 是雜訊，會稀釋相似度、還會讓「同一張圖出現在不同塊」
  製造假相似。
- **前端**：`mdImages()` 只認圖片語法，其餘照舊轉義；URL 只允許相對路徑或 `http(s)`
  （描述是使用者可編輯的內容，`javascript:` 必須擋掉）。

### 20.3 公開目錄與 URL

圖片存 **`media/kb_assets/<sha16>.<ext>`**，掛在 **`/media`**。

⚠️ 為什麼不直接公開整個 `media/`：那裡還有**客戶來訊的檔案**與**上傳的來源文件**。
只掛圖片專用目錄，其他東西維持不公開。

`kb_asset.rel_path` 仍然是「相對 `MEDIA_DIR`」(`kb_assets/xxx.png`)，
URL 由 `rag_config.media_url_of_rel()` 算：檔案在公開目錄才給 `/media/…`，
舊資料（還在 `kb/<uuid>/assets/`）回空字串 → 呼叫端退回登入端點
（**不要給一個註定 404 的公開網址**）。

### 20.4 知識庫分兩型

```
kb_collection.kind      doc | image     （舊資料一律 doc）
kb_collection.image_of  圖片庫指向它的文檔庫（獨立圖片庫 = NULL）
```

| | 文檔知識庫（doc） | 圖片知識庫（image） |
|---|---|---|
| 放什麼 | PDF / Word / Excel / Markdown… | 圖片 |
| 檢索靠 | 知識塊的文字（含內嵌圖片的標記） | 圖片的**描述**（caption） |
| 附帶 | 「`<名>_圖片庫`」**有圖才建**（見下） | 可獨立建立，也可掛在文檔庫底下 |
| 啟停用 | — | 掛在文檔庫底下時**連動**（文檔庫停 ⇒ 圖片庫停） |
| 列表顯示 | 列一張卡（附「圖片 N」＋「圖片」入口） | 附帶的那個**不單獨列卡**；獨立建立的照列 |

★ **「建庫只建這一個庫」**（2026-10-12，使用者 定案）：
- **建文檔庫不會先開一個空圖片庫** —— 否則建一個空文檔庫就多出一張空卡片。
  真正的觸發點是「這份文件真的有圖」：`kb_ingest.save_doc_assets()` 在 `assets` 為空時
  early return，`_image_collection_id()` 根本不會被呼叫。`document/move` 也一樣，
  先 `_doc_has_assets()` 才決定要不要 ensure。
- 建圖片庫也**不會**連帶建文檔庫（`collection_create` 只 INSERT 一列）。
- 例外：使用者**主動**往某個文檔庫的圖片頁「上傳圖片」時才 ensure（那是明確意圖）。
- ⚠️ **端點要用 `_assets_scope()` 解析**：文檔庫的圖**不在它自己身上**，一律落在它的圖片庫。
  `/console/kb/assets`、`/asset/upload`、`/asset/embed` 傳文檔庫 id 進來時要自動改看
  圖片庫，否則文檔庫頁的「圖片」永遠是 0 張（實測 bug）。圖片庫還不存在時回
  `no_image_lib=True` + 空集合（**不能**只回 `None`，那會被 `list_assets` 當成「全部」）。
- 刪文檔庫會**連帶刪它的圖片庫**（圖片本身變成未分組，不刪檔）。
- 文件搬家（`document/move`）時，它的圖也跟著搬到新庫的圖片庫。

### 20.5 圖片庫的檢索

圖片與知識塊**同一個候選池**排名（同權重：`0.65×cosine + 0.35×字面`），
差別只在：

- 檢索文字 = `caption`（`kb_chunk.asset_embed_text()`）；
- 回傳的 `Hit.text` = `![caption](url)`，`Hit.kind='image'`、`Hit.chunk_id` 用負數
  （避免與真 chunk id 撞號，也讓 `max_per_doc` 把每張圖獨立成組）。

**去重**：同一張圖若同時被「內嵌它的知識塊」與「圖片庫自己的條目」命中，
只留知識塊那一份（圖已經在它的文字裡了）—— 靠 `kb_asset_chunk` 判重。

### 20.6 描述 → 向量（以前完全缺失的一步）

| 時機 | 做什麼 |
|---|---|
| 寫／改描述（`/asset/caption`） | 立刻 `_embed_one_asset()` → **馬上可檢索** |
| AI 描述（`/asset/caption/ai`） | 同上（不覆蓋 `manual`） |
| 文件向量化（`embed_document`） | 連帶 `embed_assets_for(doc_id=…)` |
| 舊資料補課 | `POST /asset/embed`（UI 的「補向量化（舊圖）」按鈕） |

⚠️ `embed_document` 在「知識塊都已經向量化過」時會**提早 return** ——
那條路徑也必須處理圖片，否則「只有圖是新的」時永遠補不到（踩過）。

### 20.7 驗證

`tests/kb_asset_check.py` [6]（新增 12 條）＋ `tests/ui_check.py` [3g2]（新增 11 條）：

- chunk 文字裡有 `![題注](/media/…)`、公開路徑、alt 用題注；
- `strip_md_images()` 只留文字；
- 圖檔真的在公開目錄、URL 是 `/media/…`；
- 文檔庫有對應圖片庫（`kind=image` / `image_of=cid`）、文件的圖落在那裡；
- **圖片庫條目進得了候選池**（已修的死洞）、命中的 `text` 就是 markdown；
- 同一張圖 chunk 與圖片庫同時命中 → 只出一次；
- 文檔庫停用 → 圖片庫連動停用、檢索不到；恢復後又查得到。
- 前端：`mdImages()` 渲染 `<img>`、擋 `javascript:`、`null` 不炸；卡片分型與入口正確。

真實案例（修好後）：`图文结合输出效果如何` → **top1 0.617 命中**「圖文合并輸出效果截圖」
那張圖（修好前完全查不到）。

## 21. 兩道閘門的問題：檢索過了，卻被模型否決（2026-10-12）

### 21.1 現象與根因

紀錄 #260：

```
question     = 服务器端转发成功日志长啥样？
top1         = 0.6406            ← 命中的**就是那張截圖**（圖片庫條目）
其他 5 塊     = 欄位說明 / JSON 範例（0.18~0.24，跟「日誌長啥樣」無關）
tier/reason  = miss / no_match      send_status = not_sent
detail       = 知識庫：命中 6 塊，但模型判定資料不足以回答
```

流程是這樣斷掉的：

1. 檢索**正確**命中（門檻 0.25 已過）。
2. 入選的 6 塊交給 LLM，其中跟答案有關的那一項只有
   `![圖 1 服務器端轉發成功日志截圖](/media/…png)`。
3. **LLM 看不到圖**（設計上它只收文字）→ 它判斷「資料裡沒有任何描述日誌長什麼樣的內容」
   → 回 `__NO_ANSWER__`。
4. `looks_answered()` = False → `_rag_try()` 回 None → 降到 `TIER_MISS` → **不回復**。

⇒ 這不是檢索的問題，是**「模型有權否決已過門檻的檢索」**這個設計加上
**「答案本身就是圖」**這個情境撞在一起。純文字模型永遠不可能回答圖片題，
所以**命中得再準也沒用**。

### 21.2 修法

**(a) 提示詞（根因，最有效的一步）**

`rag_answer_prompt` 新增一條規則，並補一個 few-shot：

```
★ 資料里形如「![图注](/media/xxx.png)」的是**图片**，你看不到图片内容，但它是资料的一部分。
  遇到问「长什么样」「画面」「示意图」「截图」这类问题时，**不要**因为看不到图片就说无法回答
  —— 用图片的图注说明它是什么，并把该图片标记**原样保留**在回答里（前端会把它渲染成图）。
…
例：资料只有「![图 1 服务器端转发成功日志截图](/media/ab12.png)」，问日志长什么样
   → 答「服务器端转发成功的日志如下图所示。\n![图 1 服务器端转发成功日志截图](/media/ab12.png)」
   **不要**回 {sentinel}。
```

實測：**只改提示詞，這一題就從「不回覆」變成正確回覆**（連 `off` 模式都過）。

**(b) 檢索參數 `rag_answer_gate`（保險）**

| 值 | 行為 |
|---|---|
| `image`（預設）| 命中的塊**帶圖片**時不准否決；純文字命中仍尊重模型（維持「不硬掰」）|
| `on` | 過了門檻就一律回覆 —— **只留檢索門檻這一道閘**，模型不得否決 |
| `off` | 完全聽模型（舊行為，最保守）|

被否決時會**追問一次**（`answer_with_rag(..., require_answer=True)`，明白禁止回哨兵）；
若還是拒絕、而且命中帶圖 → 用**題注**組回覆（`請參考下圖（圖 1 …）：` + 圖片標記），
**絕不因為「模型說答不出」而不回復**。

**(c) 送出端：markdown 不能原樣發給客戶**

客戶端（WhatsApp／微信）不認 markdown，`![題注](/media/x.png)` 會變成一行看不懂的網址。
所以 `autoreply` 送出前用 `strip_md_images()` 剝掉標記，圖改由 `_send_assets()` 以**真正的圖片訊息**送出。
紀錄裡仍存完整 markdown（工作台渲染出圖）。

**(d) ★ 圖文只發一條（2026-10-12 修）**

症狀：客戶端收到「一條不帶圖的純文字」+「一條一模一樣、但帶圖的」。
根因：舊版固定「**先**發文字一條 → **再**發圖一張，而 caption 又是同一段文字」。

修法 —— 能帶 caption 的渠道就把文字塞進圖片一起發：

| 渠道 | 做法 | 客戶收到 |
|---|---|---|
| WhatsApp（`send_image(..., caption=)`）| 文字當 caption 隨圖送出 | **1 條**（圖 + 文字）|
| 微信（`send_image` 沒有 caption 欄位）| 文字一條、圖一條（**圖不帶文字**）| 2 條（先說明、後圖）|
| IG / FB | 這個服務不發圖（attachment 需要公開可抓的 URL）| 1 條（純文字）|
| 貼文留言（公開場合）| 一律不發圖 | 1 條（純文字）|

實作要點：
- 唯一判斷入口 `autoreply.assets_inline_caption(channel, scope, assets, text)`
  （也檢查文字長度 ≤ `CAPTION_MAX`(900)，避免被 WhatsApp 的 1024 上限截斷）。
- `_send_assets()` 回傳 `captioned`：**文字是否已經隨圖送出去了**。為 True 時呼叫端
  **不得**再發一條純文字（`handle_inbound` 就是靠這個旗標決定要不要 `_push_text()`）。
- ⚠️ **caption 只貼第一張成功送出的圖**（`cap_left` 用完就清空）—— 多張圖時每張都貼同一段，
  客戶端會看到同一段話重複出現。
- 圖送失敗 / 渠道不支援 → `captioned=False` → 呼叫端補發文字，**文字不會消失**。
- `reply_detail` 會帶上「（附圖 N/M）」，工作台的訊息標記與紀錄頁看得出來這條附了圖。

### 21.3 順手修掉的一個顯示 bug

`TIER_MISS` 的 `score` 原本寫成
`score = score if score is not None else rag_extra["top1"]`，
但 FAQ 未命中時 `_match_faq()` 回的是 **0.0 而不是 None** → 知識庫的 top1 被蓋掉，
